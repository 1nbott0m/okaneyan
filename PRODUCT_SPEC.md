# Личный финансовый помощник для iPhone — ТЗ MVP

**Статус:** продуктовая и техническая спецификация для первого прототипа. Банковские интеграции требуют отдельной проверки допуска, договора и схемы авторизации; наличие банковского API само по себе не означает доступ физического лица или независимого iOS-приложения.

## 1. Цель и критерии успеха

Помочь одному пользователю понять, какие деньги безопасно тратить до следующего подтверждённого поступления, и не уходить в долги из-за пропущенных обязательств. Приложение говорит прямо и объясняет расчёт; оно не стыдит, не совершает платежей и не считает запланированные покупки ошибкой.

Критерий результата: пользователь видит доступную сумму, понимает причину ограничения, учитывает предстоящие расходы и не занимает деньги из-за неверного планирования.

## 2. Границы MVP

### Входит

- iPhone, русский интерфейс, валюта RUB, локальная база и без пользовательского аккаунта.
- Автоматическая синхронизация — целевое требование MVP, но подключение разрешено только напрямую к официальному API банка из iPhone-приложения и только если банк прямо разрешает такую схему для этого приложения.
- Любой собственный/арендованный сервер, backend-посредник, агрегатор банковских данных, передача данных третьему провайдеру и серверная OAuth-прокладка исключены. Если банк требует любой из этих компонентов или не разрешает прямой native-клиент, интеграция с ним не реализуется.
- Транзакции, токены и финансовый план остаются на iPhone. Не собирать банковские логины/пароли. CSV — резервный и начальный способ импорта, пока прямой API конкретного банка не подтверждён; он не считается автоматической синхронизацией.
- Импорт операций, готовые категории, ручное исправление и правила по исправлениям.
- Если CSV явно указывает валюту строки, импорт принимает только рубли и отклоняет иностранную/неизвестную валюту без автоматической конвертации; файл без валютного поля остаётся непроверенным предположением о RUB.
- При нескольких колонках суммы импорт выбирает только явно помеченную рублёвую сумму или однозначные колонки дебета/кредита; если соответствие сумме и валюте неоднозначно, весь файл отклоняется с объяснением, чтобы не угадать неверную сумму.
- Переводы между своими счетами, регулярные поступления/расходы, поддержка от родителей как отдельный тип дохода.
- Обязательства, минимальный резерв, цели, бюджеты, долги, подписки и прогноз.
- Проверка покупки с прямым ответом и вариантами пересмотра плана.
- Напоминания о списаниях и предупреждения о риске нехватки денег.
- Удаление данных приложения с двойным подтверждением. Оно удаляет данные из локального хранилища приложения и отменяет его напоминания, но не обещает forensic-стирание SQLite/flash-памяти и не управляет ранее созданными копиями всего iPhone. База исключена из резервных копий устройства; уже сохранённые iCloud/компьютерные копии пользователь должен проверять и удалять средствами iOS/Finder/Apple Devices. Экспорт резервной копии пока не входит в прототип. См. [Apple: исключение файлов приложения из backup](https://developer.apple.com/documentation/foundation/urlresourcekey/isexcludedfrombackupkey?changes=_3) и [Apple Support: управление и удаление iCloud-копий](https://support.apple.com/en-us/108922).

### Отложено

- Платежи/переводы из приложения, кредиты и инвестиционные рекомендации, семейный доступ, мультивалюта, голосовой ввод, серверное хранение финансовой истории и облачный аккаунт.
- ИИ отложен по решению пользователя. Рассматривается возможный локальный помощник; внешняя передача данных и серверная интеграция не входят в текущий MVP.

## 3. Основные понятия и денежная модель

Хранить суммы целыми копейками (`Int64`), не `Float`/`Double`. Каждая операция хранит исходную сумму и нормализованную сумму в копейках, валюту, знак/направление, статус, дату покупки и дату проведения, источник и стабильный идентификатор источника при наличии.

- **Баланс счетов** — последнее подтверждённое банками значение по включённым счетам с отметкой времени. Если баланс недоступен, отображать «неизвестен», не вычислять его молча.
- **Доступные деньги по счетам (A)** — сумма банковских доступных остатков, без кредитных лимитов. Если API даёт только бухгалтерский баланс, явно помечать его и учитывать холды/ожидающие операции отдельно, когда они доступны.
- **Ожидаемый доход** — прогнозируемая дата/сумма, не входит в A до фактического поступления.
- **Защищённый резерв (R)** — пользовательский минимум неприкосновенного остатка.
- **Обязательства (O)** — предстоящие подтверждённые расходы до горизонта планирования: вручную заданные счета, подтверждённые регулярные платежи/подписки, транспорт и внесённые пользователем долги. Не считать историческую категорию обязательной автоматически без подтверждения.
- **Целевые резервы (G)** — деньги, отложенные на цели/запланированные покупки; не суммировать повторно с обязательствами.
- Именной резерв можно оставить отдельным или явно связать с одной накопительной целью либо конкретным экземпляром подтверждённого планового платежа. Связанные цели защищают максимум из уже сохранённой суммы цели и связанных конвертов; связанный платёж учитывает оставшееся обязательство и только превышение суммы конверта, уменьшая обе стороны на подтверждённое погашение. Старые и невалидно связанные резервы остаются самостоятельными; совпадения по названию или сумме не предполагаются. Проверка SwiftData миграции и save/reopen на iOS остаётся обязательным незакрытым пунктом.
- **Свободно до поступления (F)** = `max(0, A - R - O - G)`.
- **Можно ли купить сумму X**: разрешить только если после покупки на каждом дне до следующего подтверждённого поступления прогнозный остаток не нарушает `R` и все обязательства. Иначе запретный статус и точный дефицит/дата.
- **Остаток на день** — для контекста, не гарантия безопасности: распределить F на оставшиеся дни до следующего дохода; учитывать известные крупные платежи по их датам. Не показывать ложную точность при неизвестном доходе.

Точный прогноз расходов и проверка покупки поддерживают не более двух лет до подтверждённого поступления; за этим пределом показывать «недостаточно данных», а не разворачивать неограниченное число повторяющихся платежей. График финансового горизонта отдельно ограничен 90 днями. Дата в интерфейсе выбирается с точностью до дня, поэтому граница двух лет включает весь последний календарный день.

Модель прогноза строит дневной ряд: фактический стартовый баланс + подтверждённые ожидаемые поступления (только на дату поступления) − предстоящие обязательства − оценка переменных расходов. Оценка переменных расходов использует недавние данные и сезонность, только если есть достаточно истории; иначе отображать диапазон/«недостаточно данных» и не выдавать точечный прогноз как факт. Покупка проверяется как отдельный сценарий, не записывается как реальная операция до подтверждения пользователя.

### Статусы проверки покупки

1. **Можно** — сохраняются резерв, обязательства и активные целевые взносы.
2. **Можно с изменением плана** — покупка возможна при выбранном пользователем изменении цели/лимита/даты; показать эффект каждого сценария.
3. **Нельзя безопасно планировать** — после покупки возникнет дефицит; показать сумму и дату (например, «Не покупай сейчас: 500 ₽ не хватит на дорогу 4 ноября»).
4. **Недостаточно данных** — свежесть банковских данных/ожидаемый доход/обязательства не позволяют уверенно ответить.

Приложение не блокирует банковскую карту и не делает невозможную покупку технически невозможной. Формулировки должны описывать расчёт и риск, а не командовать или оценивать человека.

## 4. Сценарии и экраны

### Первичная настройка

1. Объяснить локальное хранение и отсутствие аккаунта.
2. Пользователь выбирает: подключить поддерживаемый банк, импортировать выписку или начать с ручной настройки плана.
3. Выбирает счета, которые входят в расчёт, и задаёт наличный остаток только при необходимости.
4. Указывает ближайшее поступление (сумма, дата, тип «поддержка от родителей» или иной) и подтверждает найденные регулярные поступления.
5. Настраивает резерв, обязательную дорогу/платежи, долги, цели и подписки.
6. Показывает результат первичного разбора и просит подтвердить неоднозначные операции.

### Главная

- «Свободно до [дата поступления]» как первичная цифра.
- «На счетах» и «зарезервировано» раскрываются отдельно.
- Следующий подтверждённый доход, ближайшие 1–3 обязательства, прогноз минимального остатка.
- Действия: «Проверить покупку», «Операции», «План».
- Свежесть синхронизации и явное предупреждение, если есть отключённый источник или импорт устарел.

### Проверка покупки

- Сумма, категория, желаемая дата; переключатель «запланированная покупка/цель».
- Результат: статус, минимальный остаток по сценарию, влияние на цель и обязательства, краткая причина.
- При дефиците показать несколько действий: перенести покупку, уменьшить/перенести целевой взнос, выбрать другой лимит/дату. Каждое действие требует явного подтверждения и показывает новый расчёт до сохранения.

### План и дашборды

- Календарь поступлений/обязательств, бюджеты по готовым категориям, цели и долги.
- Графики расходов по категориям и динамика за неделю/месяц/период между поступлениями.
- Простая оценка плана: цвет + текст + факторы; не использовать общий «оценочный балл личности». До надёжной истории операций статус должен быть «недостаточно данных», а не зелёным.

### Операции

- Поиск/фильтры по статусу операции (ожидает/проведена), категории, счёту/источнику. Возврат — тип операции, а не её статус.
- Редактирование категории, типа дохода, признака внутреннего перевода и заметки.
- Изменения классификации применяются к будущим похожим операциям; изменение прошлых операций не должно переписывать исходные данные источника.

### Регулярное и долги

- Список подписок/платежей с суммой, периодом, датой и уровнем уверенности распознавания.
- Напоминания за 1 и 2 дня — настраиваемый выбор (по умолчанию за 2 дня для крупных/обязательных платежей и за 1 день для остальных, не дублировать).
- Запись долга: кому/тип (взял/должен вернуть), сумма, дата/план возврата, состояние. Взятый долг не является обычным доходом.

### Настройки и данные

- Face ID/код, скрытие сумм одним явным жестом/кнопкой (переворот устройства не считать единственным способом из-за ненадёжности датчиков).
- Срок локального хранения истории, экспорт/импорт зашифрованной копии, удаление базы и ключей с двойным подтверждением.
- Удаление включает доступные локальные копии приложения; если пользователь экспортировал файл в Files/iCloud, приложение не может удалить его автоматически — предупредить об этом до экспорта.

## 5. Импорт и классификация

### Нормализованная операция

`id`, `sourceAccountId`, `sourceTransactionId?`, `providerTransactionId?`, `refundOfProviderTransactionId?`, `refundOfTransactionId?`, `amountMinor`, `currency`, `direction`, `merchantRaw`, `merchantNormalized?`, `descriptionRaw`, `categoryId`, `kind` (покупка/доход/перевод/возврат/комиссия/корректировка), `occurredAt`, `postedAt?`, `status`, `isInternalTransfer?`, `confidence`, `userEdited`, `createdAt`, `updatedAt`.

Поля provider ID заполняются только из однозначно распознанных, явно названных колонок выписки. При импорте в выбранный счёт точный provider ID используется для подавления дублей и повторной проверки перед сохранением; если ID отсутствует, используется отпечаток CSV с нормализованной идентичностью даты: локальная дата/время из строки не меняется при смене часового пояса устройства, а ISO-8601 timestamp с явным offset идентифицируется по абсолютному моменту. Старые timestamp-only ID продолжают распознаваться, если исходная временная зона не менялась; для уже сохранённой операции невозможно восстановить неизвестную зону, использованную до обновления приложения. Provider ID без выбранного счёта не используется для объединения операций. Повторный статус «ожидает → проведена» обновляется по отпечатку или по единственному точному provider ID в этом счёте. Если уникальный ID совпал, но сумма, дата, название или тип отличаются, операция показывается в предпросмотре как конфликт источника. Существующая запись не перезаписывается: пользователь проверяет расхождение и при необходимости исправляет операцию вручную после импорта. Изменения из банка пока нельзя автоматически применить отдельно от ручных правок.

ID возврата хранится как ссылка из источника и разрешается в локальную операцию только при одном точном совпадении расходной операции в том же выбранном счёте. Без счёта, при нуле совпадений или неоднозначности возврат остаётся отдельной операцией; суммы, даты и названия не используются для догадки. Удаление исходной операции или её перевод во входящий поток/внутренний перевод очищает локальную ссылку.

Текстовый импорт поддерживает CSV с запятой/точкой с запятой и TSV с табуляцией. Разделитель определяется по заголовку; при равной неоднозначности формат отклоняется. Кавычки в полях должны экранировать содержащиеся внутри разделители.
Строка с количеством полей больше числа заголовков отклоняется с номером строки: импорт не должен молча игнорировать лишнюю колонку, например копейки в неэкранированной десятичной запятой.

Для подтверждённой пары внутреннего перевода отдельно хранится локальная сущность `InternalTransferPair` с ID исходящей и входящей операций. При редактировании типа/даты или снятии отметки, удалении операции, выключении счёта из расчёта либо удалении счёта пара разрывается транзакционно, а сохранившаяся сторона снова учитывается как внешний денежный поток. Полная очистка данных удаляет и записи пар.

### Обработка

- Импорт идемпотентный: дедупликация по provider transaction ID; при отсутствии — консервативный ключ по счёту, дате, сумме, направлению и описанию с UI разрешения конфликтов.
- Возврат связывать с исходной покупкой, когда это надёжно; иначе показывать отдельным возвратом и не маскировать расход.
- Внутренний перевод искать парой операций между включёнными в план разными счетами по точной сумме, противоположному направлению и времени до 72 часов; показывать каждую возможную пару на подтверждение и только затем отмечать обе стороны. Нельзя автоматически скрывать одиночный или неоднозначный перевод. Matcher и интерфейс предложения реализованы; iOS runtime-поведение ещё не проверено без Xcode.
- Категории MVP: жильё, продукты, кафе/доставка, транспорт, здоровье, связь/подписки, покупки, развлечения, образование, подарки/помощь, комиссии, переводы, доход, другое. Пользователь может менять категорию; для дохода отдельный подтип «поддержка от родителей».
- Системные категории «Доход», «Возвраты», «Переводы» и «Комиссии» связаны с отдельными типами операций и недоступны для обычной покупки, выбора бюджета и правил по продавцу. Покупки остаются расходами и не могут маскироваться под другие направления в дашбордах.
- Confidence низкий — показать в очереди «проверь категорию». Правила пользователя имеют приоритет над эвристиками.
- «Импульсивная/желаемая/обязательная» — атрибут планирования, не выводить как психологический диагноз из банковского описания. Предлагать, но окончательно подтверждает пользователь.

## 6. Банковские подключения: проверенное состояние

Проверены официальные документы, доступные на 29.10.2026. Это исследование публичной документации, не тест реального аккаунта и не юридическое заключение. Пользователь установил ограничение: серверы, посредники и агрегаторы не использовать даже при наличии согласия; допускается только прямое официально разрешённое подключение iPhone-клиента к API банка.

Банк России публикует стандарты Open API для согласия и получения информации по счетам физических лиц. При этом FAQ Банка России описывает обмен как взаимодействие информационных систем организаций, соответствующих критериям участников; платформа коммерческих согласий находится в пилотировании. Это подтверждает стандартизованные сценарии данных физлиц, но не допуск частного iPhone-приложения и не доказывает, что проекту нужна лицензия. Для проекта рассматривается только прямой маршрут, официально разрешённый банком; серверная/партнёрская схема исключена решением пользователя. См. [страницу Открытых API и критерии участников](https://www.cbr.ru/fintech/api), [перечень стандартов](https://www.cbr.ru/fintech/api/prikladnye-standarty/).

### Решение по интеграционной архитектуре

- Не создавать и не подключать backend, агрегатор или посредника. Абстракция источника данных допустима только как локальный контракт для `DirectBankAPI` и `StatementImport`; не добавлять фиктивные банковские endpoints.
- Каждый прямой адаптер включается только после письменного/публичного официального подтверждения, что физлицо может подключить независимое iOS-приложение напрямую, без сервера и партнёрской прокладки; отдельно подтвердить OAuth native redirect/PKCE, разрешённое хранение токенов на устройстве, scopes, историю, частоту, стоимость и sandbox.
- Если официальный поток требует `client_secret`, mTLS-ключ, который банк не разрешает безопасно хранить на устройстве, серверного обмена кода на токен или иной посреднической инфраструктуры, такой API не использовать в этом приложении.
- Не собирать банковские логины/пароли, не автоматизировать вход в приложения банков, не использовать приватные/недокументированные API и скрейпинг.
- Разрешённые банком пользовательские OAuth-токены хранить только в Keychain; локальную транзакционную базу защищать средствами платформы. Не хранить клиентские секреты или ключи интеграции, предназначенные для backend.
- Актуальность: обновлять при открытии приложения и просить iOS о фоновой задаче для best-effort обновления. iOS не гарантирует точное фоновое выполнение. Показывать время синхронизации и статус каждого банка; расписание сервера/посредника не создавать.
- История: импортировать максимально доступный согласованный период; двухлетний период — цель, но UI показывает фактический диапазон по каждому источнику.

### Проверка варианта «только приложение на iPhone, без сервера»

- На дату проверки нет подтверждённого набора прямых API для личных счетов Сбера, Альфа-Банка и Ozon Банка, который этот проект может использовать из одиночного iOS-приложения без сервера/посредника.
- Альфа публикует методы для B2C-операций, но официальный onboarding Alfa API требует Альфа-Бизнес, договор, client integration и сертификаты. Следовательно, наличие `/pp/v1/operations` само по себе не подтверждает доступность для текущего личного MVP.
- Сбер API в доступной документации использует СберБизнес ID/организационные счета и промышленную регистрацию интеграции. Путь к личной дебетовой карте не подтверждён.
- Для Ozon Банка не найден опубликованный API чтения операций личной карты.
- Даже при разрешённой прямой авторизации банковский refresh не может быть обещан ровно каждые 12/24 часа средствами iOS background execution. Фоновая синхронизация — best effort; гарантированное расписание обычно требует серверного процесса или фонового механизма самого провайдера.
- Вывод: прямой iOS API-подключатель пока не реализовывать как будто доступ разрешён. Следующий шаг — запросить у Сбера, Альфа-Банка, Ozon Банка, ВТБ и российского ОТП подтверждение допуска частного разработчика, native OAuth redirect/PKCE и хранения токена на устройстве. Если банк требует сервер/посредника, не подключать его; оставить CSV/ручной режим для этого банка и явно показать, что автосинхронизация недоступна.

Перед реализацией адаптера банк должен подтвердить: (1) доступно ли API личному клиенту-разработчику без статуса организации/партнёра; (2) разрешён ли отдельный native iOS-клиент, а не только backend организации; (3) можно ли пройти OAuth через системный браузер с PKCE и redirect в приложение; (4) разрешены ли токены только в Keychain и обновление токена из приложения; (5) доступны ли read-only scopes на счета, остатки и операции; (6) каковы период истории, лимиты запросов и политика фонового обновления; (7) требуются ли плата, договор, сертификат/mTLS или client_secret, предполагающий доверенный сервер; (8) доступна ли песочница частному разработчику. Если нужен сервер/посредник, банк не подключается в рамках этого приложения.

### Резервный импорт выписки

- В прототипе реализован CSV. OFX/QFX и PDF отложены до получения реальных примеров выписок и проверенных правил импорта.
- Перед записью показать предварительный просмотр количества операций, диапазона дат, счетов и ошибок.
- CSV-парсер с банковскими профилями колонок, локалью чисел/дат, кодировкой; не запускать макросы/встроенный код.
- Денежный ввод и CSV принимают только значения, точно представимые в копейках. Доли копейки отклоняются с понятной ошибкой, а не округляются незаметно; дополнительные десятичные нули разрешены.
- Даты CSV разбираются по григорианскому календарю и в строгом режиме; невозможная дата отклоняет строку с её номером.
- CSV-операции с нулевой суммой сохраняются как нейтральная корректировка без дохода/расхода, а не приписываются к доходам по умолчанию.
- Для категории допускается один бюджет на месяц: повторное сохранение обновляет месячный лимит и схлопывает дубликаты; проверка покупки не выбирает случайный лимит, если обнаруживает старые дубликаты.
- При CSV с отдельными колонками «Дебет»/«Кредит» строка с заполненными ненулевыми суммами в обеих колонках отвергается как неоднозначная независимо от знаков; нельзя молча выбрать одну сторону операции.
- Импорт отменяем до подтверждения; после него допускается удалить весь импортированный пакет.
- Для каждой строки сохранять происхождение импорта и исходный текст, чтобы исправления можно было аудировать.

## 7. Локальная архитектура iOS

Рекомендация для iPhone-only MVP: Swift + SwiftUI, SwiftData или Core Data для локальной модели, Keychain для секретов, LocalAuthentication для Face ID/кода, UserNotifications для напоминаний. Выбор Swift — ради нативной скорости, интеграции с iOS и малого числа слоёв; поддерживаемую нижнюю версию iOS уточнить при создании Xcode-проекта. iOS 27 указана пользователем как желаемая целевая система, но до выпуска следует сверить доступность SDK/устройств; не ограничивать приложение только одной будущей версией без необходимости.

Слои:

1. **UI**: SwiftUI экраны и состояния загрузки/ошибки/пустых данных.
2. **Domain**: денежные типы, бюджет, обязательства, прогноз, сценарий покупки, классификация.
3. **Data**: локальный репозиторий, банковские адаптеры, парсеры выписок, дедупликация.
4. **System**: Keychain, Face ID, уведомления, фоновые задачи, импорт/экспорт.

Все вычисления денег детерминированные и покрываются модульными тестами. Источники помечаются как «банк», «выписка» или «вручную». В приложении только чтение; никакого платежного scope.

## 8. Основные сущности данных

- `Account`: банк/источник, псевдоним, маскированный номер, тип, валюта, включён в план, последний баланс и время.
- `Transaction`: нормализованная операция и исходные поля согласно разделу 5.
- `Category`, `ClassificationRule`.
- `IncomeSchedule`: тип, ожидаемая сумма/диапазон, дата/правило повторения, подтверждение пользователя.
- `Obligation`: сумма/диапазон, дата, периодичность, уровень обязательности, источник подтверждения.
- `Goal`: целевая сумма, дата, текущий резерв, гибкость (можно ли временно уменьшить взнос).
- `Debt`: сумма, кому/кому должен пользователь, срок/график, статус.
- `Subscription`: контрагент, сумма, период, следующее списание, confidence, подтверждённость.
- `ForecastSnapshot`: дата расчёта, входные данные/версия правил, горизонт и диапазон неопределённости.
- `ImportBatch` и `SyncState`: источник, диапазон, результат, ошибка, время.

## 9. Уведомления, ошибки и приватность

- Уведомления: предстоящее списание (настроенное за 1/2 дня), достижение порога бюджета, прогнозируемый дефицит до поступления, ошибка/давность синхронизации.
- Не отправлять суммы/названия операций в текст push-уведомления по умолчанию; содержание можно настроить.
- При устаревших данных не давать зелёное «можно» без оговорки: показать «данные обновлены тогда-то» и требовать ручного подтверждения баланса для решения с высокой суммой.
- Удаление: экран показывает, что именно удалится; второе подтверждение; уничтожить локальную БД, Keychain-ключи, временные файлы и локальные snapshots приложения. Отдельно объяснить, что экспортированные пользователем файлы вне контейнера приложения недоступны для удаления приложением.
- Резервная копия по умолчанию выключена. Если включить экспорт — зашифрованный архив с паролем пользователя, без банковских токенов; предложить проверить восстановление.

## 10. Нефункциональные требования

- Главный экран открывается без сети и показывает последний сохранённый расчёт и его свежесть.
- Ручная классификация операции не требует сети.
- Все суммы и даты локализованы, расчёты используют календарь устройства с явным часовым поясом.
- Основные действия доступны одной рукой; суммы можно скрыть явной кнопкой. Дополнительно в настройках можно включить двойной переворот горизонтально лежащего iPhone экраном вниз за 3 секунды; жест лишь переключает визуальное скрытие сумм и выключен по умолчанию.
- VoiceOver, Dynamic Type, контраст, Reduce Motion.
- Не запрашивать контакты, геолокацию и доступ к уведомлениям до объяснения пользы и действия пользователя.
- Локальная аналитика событий выключена; банковские описания не попадают в системные логи/краш-репорты.

## 11. План реализации до одного месяца

### Этап 0 — проверка источников данных (2–4 дня)

- Уточнить у Сбера, Альфа-Банка, Ozon Банка, ВТБ и российского ОТП допуск к чтению данных физлица для personal-use iOS app, OAuth/native redirect, scopes, историю, частоту, условия и ограничения распространения.
- Проверить у банков, разрешён ли прямой native iOS-клиент без сервера и посредника; сверить OAuth/PKCE, Keychain, read-only scopes и sandbox.
- Зафиксировать рабочий формат выписки хотя бы для одного банка.
- **Критерий выхода интеграции:** банк официально подтвердил все условия прямого доступа и предоставил sandbox. Если такого банка нет, зафиксировать конфликт требований «автоматизация» и «никаких серверов/посредников»: CSV не выдаётся за автосинхронизацию.

### Этап 1 — денежное ядро и интерактивный прототип (4–6 дней)

- Согласовать модель остатка, обязательств, резервов и следующего поступления.
- Реализовать сценарий покупки и состояния «можно / с изменением плана / нельзя / недостаточно данных».
- Прогнать примеры из реальных обезличенных выписок вручную.

### Этап 2 — локальное приложение и данные (6–8 дней)

- Онбординг, локальная база, счета/операции, категории и исправления.
- Импорт CSV/OFX с предпросмотром, дедупликацией и отменой.
- Главная, лента, план, цели, обязательства и долги.

### Этап 3 — автоматизация и обзор (5–7 дней)

- Регулярные операции, подписки, напоминания, прогноз и недельный обзор.
- Добавить один банковский адаптер только если допуск и sandbox/тестовый контур уже доступны; иначе улучшить импорт.

### Этап 4 — приватность, полировка и проверка (4–6 дней)

- Face ID, скрытие сумм, экспорт/удаление, доступность, обработка ошибок и миграции модели.
- Проверить расчёты, импорт, восстановление, устаревшие данные, дубликаты и пограничные случаи.

Сроки — оценка для одного разработчика при быстром доступе к тестовым материалам, без обещания реального банковского допуска. Подключение нескольких банков может выйти за месячный срок; импорт выписок обеспечивает полезный MVP независимо от этого.

## 12. Приёмочные сценарии

1. При остатке 1 500 ₽, резерве на дорогу 500 ₽ и нулевых иных обязательствах покупка 1 200 ₽ показывает дефицит 200 ₽; покупка 1 000 ₽ не нарушает резерв.
2. Ожидаемое поступление через неделю не прибавляется к доступным деньгам сегодня; прогноз показывает его отдельной строкой на дату.
3. Перемещение 2 000 ₽ между двумя подключёнными своими счетами не считается расходом и доходом после подтверждения пары.
4. Входящее поступление от родителей отображается отдельным типом, не смешиваясь с возвратом долга.
5. Взятые в долг 1 000 ₽ увеличивают фактический баланс, но также создают долг и не улучшают оценку устойчивости плана как обычный доход.
6. Запланированная цель не маркируется как импульсивная трата; изменение её взноса требует подтверждения пользователя.
7. Повторный импорт того же файла не создаёт дубликаты; спорные совпадения выводятся на разбор.
8. При недоступной синхронизации главный экран сообщает время последнего обновления и не показывает уверенный безопасный прогноз без оговорки.
9. Удаление стирает локальные записи и ключи; после перезапуска данные недоступны. Экспортированный файл вне приложения описан отдельно.
10. При низкой уверенности категория помечена для проверки; подтверждённое исправление применяется к будущим похожим операциям.

## 13. Решения, которые остаются на этапе прототипа

- Формула переменных расходов и достаточный минимум истории для прогноза.
- Набор и порядок категорий по твоим реальным операциям.
- Политика расчёта долга (план возврата/минимальный платёж) и гибкость целей.
- Форматы выписок, доступные в твоих приложениях банков.
- Допуск и технические условия банков для личного приложения.
- Нужен ли ИИ после прототипа; если да — локальная модель или внешний сервис с отдельным согласием.

## 14. Реализация и ограничения текущего прототипа

- Реализованы локальные модели, расчёт покупки, резервы/обязательства/цели, ручные счета, CSV-предпросмотр и категории, бюджеты, долги, цели, повторяющиеся платежи, уведомления и Face ID/код.
- Ожидаемый доход можно подтвердить для прогноза только при положительной сумме и будущей календарной дате. Поскольку в календаре выбирается только день, прогноз считает зачисление в конце выбранного дня; покупки в этот день требуют повторной проверки после фактического зачисления. Доход, ожидаемый сегодня, не считается доступным до фактического поступления.
- Месячный бюджет категории считается допустимым только для категории расходов, положительного лимита и конечной календарной даты. Невалидная сохранённая запись не используется при оценке покупки; на обзоре показывается предупреждение о необходимости исправить бюджет. Использованные расходы ограничены датой расчёта, поэтому проведённые операции с будущей временной отметкой не считаются уже потраченными.
- В разделе плана каждая запись теперь показывает понятный тип, ближайшее следующее списание повторяющегося платежа (а не устаревшую дату начала графика), статус включения в прогноз и настроенное напоминание. Разовые просроченные обязательства помечаются датой просрочки; исчерпанный график явно обозначается как завершённый.
- Добавлен цветной статус устойчивости плана: устойчиво / нужно изменить план / ниже резерва / недостаточно данных. До достаточной истории расходов безопасный статус и ответ «можно» блокируются.
- На главном экране добавлена статистика трат за текущую неделю, месяц, период с последнего фактического поступления и произвольный диапазон до 120 дней: сумма, дневная динамика, распределение по категориям и сравнение с сопоставимым периодом. Для недельного и месячного режимов сравнение идёт с предыдущими семью днями или прошлым месяцем к этой дате; произвольный период сравнивается с предыдущим интервалом такой же длины, только если он целиком попадает в загруженную историю. Период поступлений определяется по положительным фактическим доходам/входящим переводам за последние 120 дней; возвраты и подтверждённые внутренние переводы не создают границы цикла. Если истории недостаточно, сравнение не выдумывается. В выборке расходов учитываются покупки, исходящие внешние переводы и комиссии; подтверждённые внутренние переводы и операции вне периода исключаются. При скрытии сумм графики тоже скрываются.
- Раздел месячных бюджетов показывает только лимиты текущего календарного месяца; месячная сумма трат и видимые лимиты относятся к одному периоду. При удалении строки offsets сопоставляются именно с отфильтрованным списком.
- На главном экране показывается максимальный средний расход в день до следующего поступления. Расчёт учитывает свежесть баланса, резерв, цели и подтверждённые обязательства по датам; если даже без новых трат обязательства нарушают резерв, показывает дефицит, а при неполных или устаревших данных не выдаёт уверенную цифру. Это математический ориентир на основании внесённого плана, не гарантия против незапланированных расходов.
- При небезопасном прогнозе сумма дефицита и дата теперь относятся к одной точке — минимальному прогнозируемому остатку до следующего поступления. Это избегает сочетания суммы из более поздней точки с датой первого, меньшего нарушения резерва.
- Горизонтальный прогноз в MoneyCore начинается с точного текущего времени и выдаёт исходную точку плюс точки ровно на 1…N календарный день вперёд. Это исключает сокращённый горизонт из-за времени запуска и повтор последней точки; гипотетическая покупка влияет только на прогноз.
- Зарезервированная сумма каждой цели независимо ограничивается диапазоном от 0 до подтверждённой целевой суммы; повреждённое значение одной цели не может уменьшить резерв остальных целей.
- Идентификаторы счетов и целей должны быть уникальны для уверенного прогноза. При дубликатах сумма на счетах скрывается и финансовый verdict закрывается; при неоднозначных идентификаторах целей каждая сохранённая сумма остаётся отдельно защищённой, а привязанные конверты не поглощаются.
- Главная загружает ограниченный диапазон: последние 30 дней и полный текущий месяц, включая первый день 31-дневного месяца. Этого хватает графику недели/месяца, исполнению бюджета и 30-дневному прогнозу обычных расходов. Проверка покупки использует те же бюджетные правила: включает внешние списания и комиссии, исключает подтверждённые внутренние переводы и операции по отключённым/удалённым счетам; несвязанные ручные операции остаются включены.
- Проверка покупки принимает сумму, категорию, дату и отметку о предварительном планировании. Дата участвует в денежном прогнозе, категория — в сверке с месячным бюджетом. Предварительное планирование не меняет расчёт устойчивости денежных средств. Дата в прошлом и дата следующего поступления или позже не дают безопасный ответ по старому балансу.
- Вариант проверки покупки по цели рассчитывается отдельно для выбранного графика при свежих данных, надёжной истории расходов и подтверждённом поступлении. Если пользователь явно подтверждает перенос, приложение сдвигает весь ежемесячный график этой цели и её срок на один месяц, пересохраняет число и размер оставшихся взносов и обновляет напоминание. Перенос недоступен, если уже сопоставлен фактический платёж с любым будущим взносом этого графика. Код и MoneyCore сценарий покрыты проверками; SwiftData сохранение и интерфейс пока не подтверждены сборкой/запуском на iOS, поскольку в среде нет полного Xcode.
- Удаление данных сначала считывает все локальные сущности, затем удаляет их одной транзакцией. При наличии повреждённых дублирующихся записей настроек они тоже удаляются, остаётся только очищенная активная запись. После успешного сохранения очищаются ожидающие и доставленные уведомления, настройки скрытия сумм/иконки; иконка возвращается к исходной, если системный вызов успешен. Ошибка удаления показывается пользователю. Каталог базы исключается из резервных копий; Data Protection entitlement задан, а защита базы и sidecar-файлов применяется до открытия и повторно после создания SwiftData-хранилища. Подпись entitlement, реальные атрибуты файлов, физическое стирание sidecar-остатков и поведение старых резервных копий требуют проверки на устройстве.
- Формы счетов, операций, целей, бюджетов, долгов, планов и настроек показывают ошибку записи SwiftData и остаются открытыми при неудаче. Изменение локальных напоминаний выполняется после успешного сохранения модели.
- Формы редактирования счёта, операции, планового платежа и настроек теперь хранят ввод локально и меняют SwiftData только по подтверждению «Сохранить». Отмена/выход отбрасывает черновик. Проверка фактического autosave/cancel-наблюдения требует iOS runtime.
- Локальные напоминания повторяющихся платежей пересчитывают ближайшее будущее вхождение без перебора всей старой истории и обновляются при открытии/возврате приложения в активное состояние. Проверка реальной доставки и поведения после долгого закрытия приложения требует устройства.
- Настройки показывают системное разрешение уведомлений и число ожидающих платёжных напоминаний; при запрете или выключенных оповещениях дают переход в системные настройки iPhone. Ошибка постановки в очередь показывается числом затронутых планов без названий/сумм; повторная попытка происходит при следующем открытии приложения. Проверка runtime-перехода, системного отказа и обновления статуса после возврата требует устройства.
- Плановый платёж, связанный с целью, открывает её специализированный редактор, который атомарно обновляет цель и график взносов, включая точную сумму последнего платежа. Обычный редактор не может незаметно отсоединить график от данных цели.
- Проверка целостности прогноза требует, чтобы цель была связана ровно с одним подтверждённым месячным графиком взносов правильного типа и суммы; общая, потерянная или неверно настроенная связь блокирует уверенный расчёт.
- При удалении связанного планового платежа цель сохраняется, а месячный взнос и ссылка на удалённый график сбрасываются в той же транзакции. При удалении самой цели связанный график удаляется вместе с ней.

### Циклы поступлений и горизонт прогноза — 29.10.2026

В аналитике добавлен режим «С поступления»: цикл начинается с последнего положительного фактического дохода или внешнего входящего перевода в пределах загруженных 120 дней. Возвраты и подтверждённые внутренние переводы не считаются поступлениями; несколько зачислений одного календарного дня образуют одну границу. Текущий цикл заканчивается моментом расчёта; операции с будущей временной меткой не попадают в текущую сумму. Текущие расходы сравниваются с такой же по длительности частью предыдущего цикла, ограниченной датой следующего фактического поступления. При недостатке истории сравнение не показывается. Горизонт MoneyCore на N дней теперь отсчитывается от момента расчёта и не дублирует последнюю точку. Прошли 181 поведенческая проверка; SwiftUI/SwiftData в iOS остаются непроверенными без полного Xcode.
- Отдельное удаление платежа по незакрытому долгу запрещено, чтобы долг не остался без резерва платежа. При удалении связанной цели или долга системное напоминание отменяется после успешной транзакции сохранения.
- Источники дохода отделяются от категории: при добавлении дохода пользователь выбирает поддержку от родителей или другой доход; CSV распознаёт только явные упоминания родителей. Входящий перевод от родителей остаётся переводом и не становится заработанным доходом, но источник поддержки сохраняется и показывается отдельно; пользователь может исправить источник в ручной форме.
- Оценка обычных расходов требует не менее 10 исходящих расходов за минимум 13 дней в 30-дневном окне и применяет запас 15%; это стартовые параметры, их нужно проверить на личной истории.
- В оценку переменных обычных расходов не входят проведённые операции, которые пользователь явно связал с экземпляром планового платежа: этот расход уже учитывается по оставшейся сумме соответствующего обязательства. Совпадение по продавцу, сумме или дате без явной связи не используется для исключения из истории.
- CSV поддерживает UTF-8 (в том числе BOM)/Windows-1251, суммы со знаком или раздельные колонки прихода/расхода и дебета/кредита. Короткая строка не пропускается молча, а противоречивая строка с одновременным дебетом и кредитом отклоняется. Это общий парсер, а не проверенные профили всех банков; каждый формат надо сверить на обезличенных образцах.
- Автоматические подсказки категорий и типа операции в CSV сопоставляют целые слова и фразы, а не произвольные подстроки; неизвестный магазин остаётся категорией «Другое». Это снижает риск ложного бюджета, например когда «Кафельный дом» ошибочно принят за кафе.
- CSV-строки с банковскими признаками перевода разделяются по направлению: входящий перевод не считается заработанным доходом, исходящий перевод остаётся расходом, пока пользователь явно не подтвердит принадлежность обоих счетов ему. Возможные парные операции ищутся детерминированным matcher-ом; интерфейс требует ручного подтверждения обеих сторон и не меняет одиночные/неоднозначные записи автоматически.
- Изменение суммы ручного баланса требует явного подтверждения после ввода; только подтверждённая сумма получает новую отметку актуальности. Редактирование резерва, ожидаемой даты дохода, названия счёта или его включения в расчёт не должно делать старый остаток свежим.
- Перед импортом можно выбрать локальный счёт. UUID выбранного счёта сохраняется в каждой импортированной операции и позволяет фильтровать общую ленту операций по счёту. Source ID формируется из хеша идентификатора счёта и данных строки, поэтому повтор того же ряда из файла в другом расположении распознаётся; одинаковые отдельные операции внутри одного файла получают разные ID. Без привязки к счёту сохраняется исходная идентификация по выбранному файлу и показывается предупреждение о возможных дублях. Это row fingerprint, не provider transaction ID: меняющийся текст описания может не совпасть; регистр и пробелы в описании нормализуются. Дата без offset сохраняет календарные поля источника независимо от часового пояса устройства; ISO-8601 с offset использует абсолютный момент. Старые timestamp-only fingerprints совместимы при прежней временной зоне, но старый часовой пояс из такого ID восстановить нельзя. Операции, импортированные до добавления необязательного поля счёта, остаются без привязки; проверка миграции существующего SwiftData store требуется на полном Xcode.
- Баланс из настроек используется только как резервный источник, пока нет ни одного отдельного счёта. При добавлении счетов он не складывается с их остатками; если сохранённая сумма была наличными, пользователь может явно перенести и подтвердить её как отдельный счёт «Наличные». Это предотвращает двойной учёт и делает исключённые/наличные остатки видимыми.
- CSV-предпросмотр показывает количество новых и повторяющихся строк, отмечает каждое совпадение и строит предложения о регулярных положительных внешних исходящих тратах (покупки, переводы и комиссии) только на основе новых строк. Подтверждённые внутренние переводы и невалидные суммы исключаются. Идентификация и поиск регулярных трат вычисляются в фоновой задаче. Совпадения пропускаются после явного подтверждения импорта. Ожидающие проведения новые строки посчитаны отдельно; предпросмотр поясняет, что они не участвуют в финансовой аналитике и что импорт не обновляет доступный баланс.
- Прямых подключений Сбербанка, Альфа-Банка, Ozon Банка, ВТБ и ОТП Банка пока нет. Реального банковского OAuth и синхронизации нет; баланс счёта вводится вручную. Автосинхронизация обязательна для целевого MVP, а ежедневная загрузка выписок пользователю не подходит. Текущий прототип не удовлетворяет этому требованию; P2 считается заблокированным, пока банк не подтвердит direct iOS personal API без backend либо владелец не пересмотрит запрет на сервер/посредника. Это не вывод о том, что приложение обязано иметь лицензию.
- Внешний ИИ не реализован. Расчёт финансовой доступности детерминированный и локальный.
- Исправленную категорию можно запомнить для будущих импортированных операций с совпадающим нормализованным названием получателя. Сопоставление намеренно точное, чтобы не переносить ошибочную категорию на посторонние операции; изменения задним числом не применяются.
- Экспорт/восстановление резервной копии не реализованы. Удаление приложения удаляет записи из локальной базы приложения; отдельные экспортированные файлы не управляются приложением.
- Поведенческие проверки ядра проходят; синтаксис Swift-файлов и формат Xcode-проекта проверяются отдельно. Редактирование цели пересчитывает связанный график взносов и резерв, последний взнос ограничивается остатком, а срок учитывает фактический календарный день ежемесячного списания. Некорректная сумма финального взноса не может увеличить плановый платёж. Свежесть объединённого баланса определяется по самому старому времени обновления включённых счетов; без банковских счетов сохраняется свежесть ручного баланса. Импорт различает входящие и исходящие переводы; старые строки остаются дедуплицируемыми после переклассификации. Для файлов приложения задана системная защита iOS и исключение хранилища из резервного копирования; установка entitlement и поведение на устройстве не проверены из-за отсутствия полного Xcode/iOS SDK.
- Переключатель Face ID/кода использует `LAContext.evaluatePolicy` как дополнительную экранную блокировку, а не как криптографический замок базы. Экран блокируется при переходе приложения в `inactive` или `background`, чтобы скрыть финансовый экран при уходе и снимке в переключателе приложений. Устройство и его код остаются основной границей защиты; для блокировки именно базы отдельным секретом потребуется совместимое с SwiftData шифрование, которого пока нет. Порядок lifecycle-событий нужно подтвердить на iPhone.
- Ошибка открытия хранилища больше не должна завершать приложение через `fatalError`: показывается экран с причиной и повторной попыткой. Сам сценарий отказа SwiftData не удалось воспроизвести без iOS runtime.

### Точность повторяющихся платежей (29.10.2026)

- Месячные повторы теперь сохраняют исходное число месяца: при платеже 31-го числа февральская дата будет последним днём февраля, а в марте снова 31-е. Для календарных расчётов используется григорианский календарь с локальной временной зоной устройства.
- Прогноз и планировщик локальных уведомлений теперь вызывают одно правило следующего календарного повтора. Напоминания о платеже 31-го числа больше не дрейфуют на 28-е после февраля; годовщина 29 февраля возвращается на 29-е в високосном году.
- Отрицательное число оставшихся повторов трактуется как исчерпанное, не создавая фиктивных обязательств.
- Поведение покрыто тестами на обычный февраль, високосный год, исчерпанный лимит повторов и некорректный отрицательный лимит.

- Распознаватель регулярных операций также сохраняет исходное число месяца, когда предлагает дату следующего списания: последовательность 31 декабря → 31 января → 28 февраля предложит 31 марта, а не 28 марта. Он использует общий календарный расчёт с планом и напоминаниями.

### Основа сверки оплаты с планом (29.10.2026)

- Добавлены чистые правила MoneyCore для явно подтверждённой пользователем связи конкретной проведённой операции-расхода с конкретным вхождением планового платежа. Совпадение по дате или сумме само по себе не выбирает операцию.
- Поддержана частичная оплата; операция не может быть связана повторно, а внутренний перевод, ожидающая операция и переплата отклоняются. Дублирующие ссылки на один ID или дата вне расписания не уменьшают остаток обязательства. Все прогнозные расчёты MoneyCore теперь резервируют только неоплаченный остаток; старый JSON-снимок без ledger декодируется с пустым списком сверок.
- В редакторе проведённой операции пользователь может явно выбрать плановый платёж и конкретную дату его повтора. При построении снимка приложение перепроверяет операцию, план, дату, уникальность связи и то, что баланс обновлён после операции; для операции без счёта проверяется самое старое время обновления включённых счетов. Операции с отключённого или удалённого счёта не погашают обязательства в активном финансовом плане; ручные операции без счёта остаются допустимыми. Неподтверждённые связи в прогноз не попадают. Редактирование без выбранного плана снимает связь, удаление операции удаляет её вместе с источником, удаление плана, цели или долга в одной локальной транзакции очищает ссылки на соответствующий план.
- Связь хранится в двух новых необязательных полях существующей SwiftData-операции; это предназначено для автоматической лёгкой миграции, но фактическая миграция, UI type-check, сохранение и перезапуск пока не проверены без полного Xcode/iOS SDK. При декодировании неполного JSON без явного признака надёжности прогноза используется безопасное значение `false`.


### Защита от некорректных знаков в финансовом плане (29.10.2026)

- Резерв, целевой резерв, сумма обязательства и прогноз обычных дневных расходов не могут становиться отрицательными входами расчёта. Иначе отрицательный платёж или прогноз расходов превращался в фиктивное увеличение доступных денег.
- Отрицательные банковские остатки не нормализуются: они могут отражать реальный минус на счёте.
- Добавлены регрессионные проверки расчёта доступной суммы и вердикта покупки на искажённых знаках. Текущее ядро проходит 67 проверок.


### Привязка импортированной операции к локальному счёту (29.10.2026)

- Выбранный при импорте счёт теперь записывается как необязательный `sourceAccountID` у каждой операции. В ленте можно фильтровать операции по выбранному счёту, а строки показывают банк и имя счёта. Ручные операции без выбранного счёта остаются в общей ленте и в расчётах.
- Отключённые и удалённые счета не участвуют в прогнозе переменных расходов, дашборде расходов и исполнении бюджетов. Удалённый счёт не стирает историю: операции остаются в общей ленте, но для включения в текущий план их нужно вручную привязать к действующему счёту.
- Удаление счёта не удаляет его историю; у операции со старым идентификатором показывается «Счёт удалён».
- Добавление nullable-поля требует проверки миграции ранее созданного SwiftData store на полном Xcode/симуляторе; синтаксическая проверка исходника эту миграцию не подтверждает.


### Производительность истории операций (29.10.2026)

- Главный экран запрашивает недавние операции за 30 дней, а лента истории SwiftData загружает страницу до 100 записей и позволяет листать полную историю, сохраняя фильтр счёта и редактирование/удаление.
- Фильтр категории и регистронезависимый поиск магазина/получателя применяются в запросе SwiftData и сочетаются с фильтром счёта; смена фильтра возвращает ленту на первую страницу.
- Статус «ожидает/проведена» хранится для новых операций и импортируется из CSV при наличии столбца статуса; повторный импорт продвигает известную ожидающую операцию в проведённую без дубликата. Выписки без статуса по умолчанию считаются проведёнными; неизвестное значение статуса отклоняется. Старые операции без сохранённого статуса трактуются как проведённые. Полный iOS compile и SwiftData migration пока не проверены.
- Для проверки дублей импортированной выписки ID источников читаются отдельным `@ModelActor`, не через главный UI-контекст; во время разбора и сверки показывается индикатор.
- Парсинг, запросы и прокрутка должны быть проверены на реальном iPhone и полном Xcode. Из-за отсутствия Xcode компиляция SwiftUI и измерение задержки на устройстве пока не подтверждены.


### Учёт переводов и комиссий в расходах (29.10.2026)

- Обычные исходящие переводы другим людям и банковские комиссии теперь входят в аналитику расходов, прогноз обычных трат и бюджеты. Подтверждённые внутренние переводы исключаются из этих показателей.
- В ручном вводе тип «Перевод» выбирает категорию переводов и предлагает явное подтверждение «между моими счетами». До подтверждения такой перевод считается расходом. При смене категории с переводов внутренний флаг сбрасывается.
- К ядру добавлен `TransactionKind.isOutflow`, единый признак для покупки/перевода/комиссии; тесты проверяют внешний перевод и комиссию в суммах, категориях и дневном прогнозе. Core suite: 67 проверок.


### Отдельная классификация возвратов (29.10.2026)

- Положительная CSV-операция с явными словами «возврат», «возмещение», `refund` или `reversal` теперь импортируется как возврат с категорией «Возвраты», а не как доход. Возврат не увеличивает оценку регулярных доходов и не маскирует исходные расходы в аналитике.
- В ручном вводе добавлен тип «Возврат» с входящим отображением суммы.
- Повторный импорт совместим с предыдущей классификацией: отпечаток старой строки со статусом обычного дохода сопоставляется с новой строкой возврата как для выбранного счёта, так и для не привязанного к счёту импорта.
- Добавлены три проверки распознавания и защиты от дублей. Текущая проверочная команда выводит 70 успешных проверок ядра.


### CSV: логические записи и переносы внутри кавычек (29.10.2026)

- Парсер больше не считает каждый физический перевод строки границей операции, если строка находится внутри кавычек. CRLF, в том числе внутри кавычечного поля, нормализуется в перевод строки текста; точка с запятой в таком поле не делит столбец.
- Незакрытая кавычка теперь возвращает отдельную понятную ошибку с номером начальной строки записи.
- Регрессионные проверки покрывают поле с `;` и CRLF внутри кавычек, следующую операцию и повреждённое незакрытое поле. Проверочная команда ядра проходит 72 проверки.


### Проверка 2026-10-29 — типы и правка операций

- Формы добавления и редактирования поддерживают покупку/расход, доход, внешний или внутренний перевод, возврат и комиссию. При смене типа приложение сбрасывает несовместимые категорию и признак внутреннего перевода; корректировки старого формата остаются отдельно обозначены и не трактуются как доход/расход.

### Отрицательный баланс счёта — 29.10.2026

Формы ручного счёта и общего баланса принимают отрицательную сумму, чтобы можно было явно записать овердрафт или задолженность по счёту. Резерв и ожидаемый доход остаются неотрицательными. Проверки ядра подтверждают, что отрицательный баланс не превращается в доступные деньги и блокирует даже небольшую покупку. Сейчас проходит 82 проверки.


### Обязательства в день поступления — 29.10.2026

Доступная сумма на главном экране теперь резервирует подтверждённые платежи, назначенные ровно на день ожидаемого поступления. Время списания и зачисления неизвестно, поэтому приложение консервативно учитывает списание раньше поступления; ожидаемый доход всё равно не считается доступным. Добавлен регрессионный сценарий; проходят 83 проверки.

Это статус «не подтверждено», а не утверждение, что API юридически или технически отсутствует. **Уточнение по Open API Банка России (29.10.2026):** опубликованы отдельные рекомендованные стандарты для счетов физических лиц, включая методы согласия и чтения счетов/балансов/операций. Это означает, что технический профиль для розничных данных существует; он не означает, что частное приложение стало допущенным потребителем данных. FAQ Банка России описывает участников Open API как организации, отвечающие критериям, а для физлицев спецификация согласия использует client credentials и JWS-подпись. Не считать такую схему доступной без сервера/посредника или разрешённой для MoneyWise, пока банк письменно не подтвердит регистрацию приложения и безопасное native OAuth/token flow. Это также не является заключением, что нужна лицензия. Источники и подробности: [анкета проверки API банков](.agent/bank-api-eligibility.md#уточнение-по-стандартам-банка-россии--29102026).


### Уточнение учёта долга — 29.10.2026

Автоматическое уменьшение введённого остатка только по прошедшим датам отключено: оно ошибочно предполагало, что каждый платёж реально внесён, и не учитывало проценты/пропуски. Остаток долга теперь хранит последнее подтверждённое пользователем значение; для обновления добавлен экран редактирования долга. Регулярный платёж остаётся в прогнозе каждый месяц до явного нулевого остатка. Проверка целостности также требует уникальную связь одного долга с одним подтверждённым месячным планом; при разделяемой или неверной связи уверенный расчёт блокируется.
